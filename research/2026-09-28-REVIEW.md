## New JARVIS pack

Source: [JARVIS with Claude Opus 5.5](https://www.skool.com/aiworkshop-lite/classroom/5b3aa9e5?md=d670bd8f5f2c48cdb086c006335a007e), Jarvis-Opus-5.5-Prompt-Pack.pdf. All 24 pages of extracted text read end to end; page visuals and the 14:24 video remain unreviewed. The original stays local. This brings the acquired community PDF total to 13 files / 139 pages. Its model availability, price and performance assertions are author claims, not verified provider facts.

The foundation repeats graph indexing, source highlighting, note capture, speech buffering, screen questions, model switching and preflight. The new material adds owner callbacks, Google tools, Telegram, conditional standing orders, reminders, morning briefings, inbound phone verification, staging and a security review. It is still a build prompt pack, not the paid implementation.

**Adapt:** explicit distinction between immediate calls and conditional standing orders; exact model IDs; short outcome receipts; one-use pairing with expiry/attempt limits; server-side caller verification; per-event deduplication; dry runs; refusal to serve configuration; authenticated phone instructions linked to resulting task receipts. These are requirements for native contracts, not instructions to create accounts, buy numbers or place calls now.

**Correct before implementation:**

- The briefing prompt silently skips failed sources. Report incomplete coverage briefly and retain the failed-source receipt; otherwise an apparently complete briefing can omit urgent information.
- A spoken transcript is evidence to parse, not authority by itself. Bind instructions to a verified call, speaker, tool scope, explicit action and conditions. Resolve dates/timezones, ambiguity, replay and stale conditions before execution. The prompt's blanket statement that the call already approved everything is insufficient.
- Updating one shared provider agent prompt before dialing can race across calls. Require call-specific immutable context or provider isolation; actual Retell behavior is still unverified.
- Polling avoids accepting inbound call-completion webhooks, but is not a universal anti-forgery guarantee. Authenticate provider requests and reconcile call IDs, account and terminal state.
- A simple state file and a card ID do not prove crash-safe scheduling or exactly-once external delivery. Use transactionally recorded dispatch attempts and provider reconciliation; ambiguous delivery stays unknown rather than being blindly retried.
- An offline reminder needs an explicit late-delivery policy, expiry, timezone/DST behavior and cancellation semantics. A powered-off laptop cannot deliver reminders until it runs again; closing a browser differs from shutting down the host.
- UNIX chmod instructions do not establish Windows protection. Verify Windows ACLs and secret storage. Keep tunnel access tokens out of query strings where possible; provider-supported authentication needs review. Do not expose the entire desk through a tunnel.
- Caller-ID hints are insufficient. Lockout needs a trustworthy key and abuse limits beyond caller ID; authentication must bind each tool request to a verified call, not merely a model-supplied boolean.
- “Consider it done” remains misleading before execution. Acknowledge acceptance, then confirm the actual result from receipts.

## Official standards and storage evidence

The complete extracted text of the [MCP security guide, version 2025-11-25](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices) was captured and read. It requires token-audience separation, per-client consent in proxy flows, request authorization independent of session IDs, safe OAuth URL handling and limited scopes. Its local-server guidance reinforces isolating process privileges. **Design consequence (our inference):** keep the MCP gateway, provider credentials and local executor as separate authority boundaries. MCP compatibility alone will not make arbitrary tools safe. Linked authorization standards and diagrams are not covered by this text review.

The complete [SQLite WAL guide](https://www.sqlite.org/wal.html) was captured and read. WAL supports concurrent readers with a single writer, requires same-host storage, and needs checkpoint management. Long readers can impede checkpoints; busy errors remain possible. The WAL file can contain committed state and must not be discarded during backup. The guide identifies a WAL-reset fix in 3.51.3 and specified backports. **Design consequence (our inference):** SQLite is a candidate for the local catalog, pending actual bundled-version inspection, power-loss policy, migration, backup and concurrent/restart tests. No SQLite database or persistence guarantee was implemented in this wave.
